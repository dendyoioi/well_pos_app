# 1. OBJECTIVE

Harden the executable migration artifacts so that PostgreSQL enum handling is:

1. exactly aligned with Target Database Schema Revision 4;
2. fail-closed when a pre-existing enum is incompatible;
3. explicit about enum ownership;
4. reversible with respect to objects created by this migration;
5. non-destructive toward pre-existing compatible enums;
6. free from unsafe assumptions such as subset compatibility;
7. fully reflected in:
   - preflight,
   - ownership registry,
   - rollback,
   - object inventory,
   - reconciliation,
   - validation tests.

This prompt MUST NOT redesign Target Database Schema Revision 4.

# 4. TARGET ENUM CONTRACT

Read the exact enum declarations from Target Database Schema Revision 4.

The migration currently targets 20 enums.

Build an explicit machine-checkable contract containing, for EVERY enum:

- enum name
- exact ordered target labels
- target label count
- source location in Target Schema Revision 4

The comparison MUST be exact.

Do NOT use:

- subset compatibility
- superset compatibility
- "contains all required labels"
- "compatible enough"
- name-only matching

For an existing enum:

```text
existing labels == target labels
```

must be true for it to be classified as:

`PRE_EXISTING_EXACT_COMPATIBLE_REUSED`

Ordering MUST be compared as part of the contract if PostgreSQL enum ordering is part of the declared target definition.

If exact equality cannot be established, the result is NOT exact compatibility.

---

# 5. ENUM OWNERSHIP STATES

Every target enum MUST resolve to exactly one of these states:

## A. CREATED_BY_PROMPT_12_4_2

The enum did not exist before this migration and is created by this migration.

Ownership:

```text
OWNED
```

Rollback:

```text
DROP TYPE <enum> only if ownership registry proves this migration created it
```

The rollback MUST NOT drop an enum merely because it exists.

---

## B. PRE_EXISTING_EXACT_COMPATIBLE_REUSED

The enum existed before this migration and its complete definition exactly matches Target Schema Revision 4.

Ownership:

```text
PRE_EXISTING
```

Rollback:

```text
PRESERVE
```

The rollback MUST NOT modify, rename, replace, or drop it.

---

## C. PRE_EXISTING_INCOMPATIBLE

The enum existed before this migration but its definition differs from the target contract.

This includes:

- missing labels
- extra labels
- different label ordering
- different enum identity where relevant
- any other contract mismatch discovered by the exact comparison

Result:

```text
FAIL CLOSED
```

The migration MUST NOT:

- ADD VALUE
- DROP VALUE
- rename labels
- recreate the enum
- cast existing columns
- replace the enum
- silently mutate the pre-existing enum

No migration execution may proceed after this condition.

---

## D. UNKNOWN / UNVERIFIED

If the migration cannot establish ownership or exact compatibility, classify the enum as:

```text
UNKNOWN / UNVERIFIED
```

Result:

```text
FAIL CLOSED
```

Do not guess.

---

# 6. NO SUBSET LOGIC

Remove any logic equivalent to:

```text
existing labels are a subset of target labels
```

or:

```text
target contains existing labels
```

or:

```text
required labels are present
```

Such logic MUST NOT be used to authorize reuse.

The only valid reuse condition is exact contract equality.

Document this explicitly in the validation report.

---

# 7. NO ENUM MUTATION DURING EXPAND

Prompt 12.4.2 MUST NOT mutate a pre-existing enum.

In particular, do not use:

```sql
ALTER TYPE ... ADD VALUE
```

against a pre-existing enum as part of the reusable Expand migration.

Do not use:

```sql
ADD VALUE IF NOT EXISTS
```

as a compatibility mechanism.

Reason:

- it can hide vocabulary drift;
- PostgreSQL enum value removal is not symmetric;
- rollback cannot safely restore an arbitrary pre-existing enum definition by simply dropping a label.

If a pre-existing enum differs from the target contract, fail closed.

Any future enum transformation must be handled as a separately authorized migration outside this prompt.

---

# 8. CREATE TYPE SAFETY

For each target enum:

1. inspect whether it already exists;
2. if it does not exist, create it with the exact target labels;
3. register ownership as `CREATED_BY_PROMPT_12_4_2`;
4. if it already exists, compare the complete definition before reuse;
5. classify it as either:
   - PRE_EXISTING_EXACT_COMPATIBLE_REUSED
   - PRE_EXISTING_INCOMPATIBLE
   - UNKNOWN / UNVERIFIED.

Do not use `CREATE TYPE IF NOT EXISTS` as the ownership mechanism.

`IF NOT EXISTS` MAY ONLY be used if exact preflight has already established the correct ownership/compatibility semantics and it cannot weaken fail-closed behavior.

Prefer explicit existence checks with explicit classification.

# 10. OWNERSHIP REGISTRY

The ownership registry MUST record enum ownership explicitly.

Required fields or equivalent semantics:

- object_type
- object_name
- ownership
- compatibility_state
- created_by_migration
- rollback_action

If the existing registry schema cannot represent these semantics, update the registry artifact within this prompt.

Registry lifecycle MUST itself be safe.

- blindly DROP the registry;
- assume registry existence implies ownership;
- overwrite ownership records without controlled semantics.

The registry MUST distinguish:

```text
OWNED
PRE_EXISTING
```

and MUST preserve enough information for rollback to act safely.

# 11. ROLLBACK CONTRACT

Rollback rules:

### CREATED_BY_PROMPT_12_4_2

Allowed:

```sql
DROP TYPE ...
```

ONLY when the ownership registry proves that this migration created the enum.

### PRE_EXISTING_EXACT_COMPATIBLE_REUSED

Required:

```text
PRESERVE
```

No DROP.

No ALTER.

No rename.

### PRE_EXISTING_INCOMPATIBLE

Migration must never proceed, therefore rollback of an executed migration must not be used to repair the incompatible enum.

### UNKNOWN / UNVERIFIED

Migration must never proceed.

Rollback MUST NOT guess.

---

# 12. ROLLBACK ORDERING

If an enum was created by this migration and target tables/columns depend on it, rollback must respect PostgreSQL dependency order.

Therefore:

1. remove only migration-owned dependent objects first;
2. then drop migration-owned enum types;
3. never drop a pre-existing enum.

Do not create a rollback that can destroy unrelated/pre-existing schema objects.
